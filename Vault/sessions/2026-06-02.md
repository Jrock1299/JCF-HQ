## What changed

### 1. Edge OANDA orders forbidden — diagnosed, blocked on token
- `auth-profiles.json` only has `oanda:default` keyed to **account 001**
  (`101-001-22502524-001`). Code in `edge_oanda.py` falls back to this when
  `oanda:scalper` isn't present (and it isn't).
- The `oanda:default` token *does* list both 001 and 002 in `/v3/accounts`,
  but per-account access returns 403 for 002 (`{"errorMessage":"The provided
  request was forbidden."}`). Verified end-to-end with curl.
- Conclusion: this is a token-authorization issue at OANDA's side, not a
  wrong account ID in config. The token was generated without authorising
  the Scalper sub-account 002.
- **Action required from Jase** (cannot fix in code):
  1. Log into OANDA practice → *Manage API Access* → regenerate the personal
     access token with both sub-accounts (001 + 002) ticked, **or** create
     a separate token while account 002 is active.
  2. Add it to `agents/main/agent/auth-profiles.json` as a new
     `oanda:scalper` profile:
     ```json
     "oanda:scalper": {
       "type": "api_key",
       "provider": "oanda",
       "key": "<NEW_TOKEN_HERE>",
       "account_id": "101-001-22502524-002"
     }
     ```
     `edge_oanda.py` already prefers `oanda:scalper` over `oanda:default`
     when its key is present and doesn't start with `PASTE_`.
- See [[../agents/edge]].

### 2. session_end_notify reading wrong Blade source — fixed
- `scripts/session_end_notify.py` read `dashboard/agent_trades.json`, which
  Blade hasn't written to since the D3 cutover (last entry there is dated
  2026-05-18 from Edge). Blade's actual trade sink is
  `dashboard/blade_learning_log.json`.
- Repointed `load_blade_trades()` to the learning log and normalised the
  field names (`outcome → result`, `pnl_usd → pnl`, `timestamp_close →

- Verified end-to-end against today's LONDON: script now reports 4 trades,
  +$255.95 (DE30_EUR pos1/2/3 + CHF_JPY pos1). Note: 4 records present —
  CHF_JPY pos2/pos3 were not flushed to disk, almost certainly because the

- See [[../infrastructure/system-architecture#session-end-pipeline]] and
  [[../agents/blade]].

### 3. blade_balance.json never created — fixed
- Root cause: cron wraps each session with `timeout 7200`, but LONDON runs
  4h and ASIA runs 6h. SIGTERM kills the process at the 2h mark, long
  before the natural session-end path that calls `_save_paper_balance()`.
- `agents/blade/bot/blade_bot.py`:
  - Installed `signal.SIGTERM` / `signal.SIGINT` handlers inside
    `run_session()` that persist `paper_balance` before exit.
  - Added a per-tick save inside the main monitor loop so even a kill -9
    (which can't be caught) loses at most 30 seconds of state.
- Seeded `dashboard/blade_balance.json` with the in-process LONDON-close
  value of **$5,064.35** so it's preserved across the running NY_PM (which
  still has the pre-fix code in memory until next session start).
- See [[../strategies/blade-d3-sizing#compounding-persistence]] and
  [[../agents/blade#compounding]].

### 4. Telegram 400 + false "Sent." log — fixed
- Two-part bug in `scripts/session_end_notify.py`:
  - `CHAT_ID = os.environ.get('TELEGRAM_CHAT_ID', '')` — that env var
    doesn't exist; the rest of the codebase uses `TELEGRAM_ALERT_CHAT_ID`.
    Empty `chat_id` → Telegram 400 "chat_id is empty".
  - `send_telegram()` swallowed the HTTPError, and `main()` logged "Sent."
    unconditionally → false success.
- Fixes:
  - `CHAT_ID = os.environ.get('TELEGRAM_ALERT_CHAT_ID') or os.environ.get('TELEGRAM_CHAT_ID') or ''`
    (matches the convention used by Lens / Norman / Victoria).
  - `send_telegram()` now returns `True/False`, surfaces Telegram's actual
    error body, and `main()` logs accordingly + exits non-zero on failure
    so cron flags real failures.
- Verified end-to-end: today's LONDON message actually delivered (message
  ID returned by Telegram).
