## 1. Lens fired three times with raw debug output — FIXED

**Reported.** Three Telegram messages in one morning: one real macro report and
two that opened with raw `[provider-transport-fetch]` / `[model-fetch]`
transport logs, one of those also reporting "Data unavailable, standing down"
on SPX/DE30/XAU.

**Not duplicate crons.** The crontab has no duplicate Lens lines. Lens has
**three distinct scheduled sends per weekday** and always has:

| Time (UTC) | Job | Product |
|---|---|---|
| 04:55 | `run_lens_brain.sh` | daily macro thesis |
| 06:00 | `run_lens_regime.sh` | pre-London regime brief |
| 12:00 | `run_lens_regime.sh` | pre-NY regime brief |

Three messages is by design (documented in `run_lens_regime.sh`'s own
scheduling note). What made it *look* like a malfunction is that the two regime
briefings were both garbage. Fix the garbage, not the schedule.

**Root cause — a three-link chain.**

1. Codex hit its subscription limit on 2026-07-27 (resets Aug 23). Both
   `gpt-5.6-terra` and `gpt-5.5` now return 429 on every regime run.
2. The chain falls through to `openrouter/auto`, which **succeeds** — but the
   openclaw CLI emits `[provider-transport-fetch]` transport lines *before* the
   `model.run via` metadata block.
3. `call_codex()` stripped the header by walking from line 0 and `break`ing on
   the first line it didn't recognise. The transport lines are not in its list
   of four known prefixes, so it broke at line 0, `body_start` stayed 0, and
   **the entire stdout became "the narrative"** — and was sent to Telegram and
   posted to the Agent Hub.

The leak started 2026-07-28 and hit **every** regime briefing since: 6 messages
over 3 days, confirmed by scanning `dashboard/agent_hub.json`.

**Fixed at two layers.**

- **Destination (the real guarantee).** New `scripts/output_sanitizer.py`;
  `telegram_personalities.wrap_message()` now sanitises every body it wraps.
  ~20 scripts shell out to a model CLI and any of them can grow this defect,
  with a silent failure mode — so the guarantee lives at the destination rather
  than in each caller's parser. Debug output cannot reach Telegram regardless of
  what else goes wrong upstream. A body that is *entirely* noise becomes an
  explicit "no usable output" notice, never an empty bubble and never a dump.
  Deliberately conservative: prose never matches, and the rules require either a
  known machine-log shape or ≥4 `key=value` tokens on one line.
- **Source.** `call_codex()` in `run_lens_regime.sh` and the identical parser in
  `scripts/h4_read.py` now scan every line instead of trusting the ordering, and
  log what they filtered to the run log — where the transport detail belongs.

**Two more fixes in the same area.**

- **One delivery per scheduled slot.** A `/tmp/lens_regime_sent_<UTC-date>-<hour>.lock`
  guard makes a double-fire, an overlapping manual run, or a retry wrapper
  physically unable to send twice. No lock is written on send failure, so a
  genuine retry still delivers. Override: `LENS_REGIME_FORCE_SEND=1`.
- **The log was double-writing.** Every line went through `| tee -a "$LOGFILE"`
  pointed at the same file cron already appends to — so `logs/lens_regime.log`
  recorded everything twice, including `Telegram delivered`. That is what made a
  single correct send read as a double-send while diagnosing this. One writer now.

**"Data unavailable" was a real second bug, not just cosmetic.** The token was
never the problem — replayed minutes later, the same credential returned 200
with full candles on all three instruments. At 12:00 UTC three jobs fire on the
same cron minute (the regime briefing plus Blade's and Edge's turtle ticks) and
share one practice token; OANDA answers part of that burst with **401
"Insufficient authorization"**, which reads like an auth failure and isn't one.
A single-shot fetch turned that blip into a whole instrument going dark.

New `scripts/oanda_retry.py` — bounded retry (3 attempts, exponential backoff)
on transient markers only, wired into `lens_regime.fetch_oanda_candles`,
`live_turtle_executor.fetch_candles` and `account_summary`. **This is not a way
to manufacture data:** if every attempt fails the caller still reports the gap
honestly. Retrying a flaky read is not substituting a stale value for a failed
one — Rule #9 is untouched.

**Verified end-to-end.** A full live run with the send blocked by the new lock:
6 debug lines filtered to the log, clean narrative written, send correctly
skipped, log lines appearing once — and **all four instruments returned real
data**, no "standing down".

## 2. Victoria's net worth drifting $36,578 → $38,578 → $41,578 — FIXED

**Root cause: there was no net-worth computation anywhere.** `net_worth` was a
field in the JSON *output template* the model fills in. Victoria was handed a
list of account balances and asked to total them, so the reported figure moved
with whatever model happened to answer that run.

The drift decodes exactly:

| Reported | Delta | What it was |
|---|---|---|
| $36,578.25 | — | correct: the exact sum of the real-money feeds |
| $38,578.25 | +$2,000 | invented, no source |
| $41,578.25 | +$5,000 | **Edge's paper balance**, counted as net worth |

Today's stored report said $41,578.25 — the paper-money case.

**Fix.** `compute_net_worth()` in `victoria_brain.py` sums the real feeds in
Python and returns the total *with* a per-source breakdown, per-source age, and
a stale flag. It is injected into the prompt as an authoritative value the model
must quote — and then, because a prompt instruction is not a gate (Critical Rule
#10), **overwritten in the result after the model returns**, with the
disagreement logged. Same pattern already used for API costs.

Paper money is excluded by construction (Alpaca/Jerry, OANDA practice books) and
listed under `excluded` so the omission is visible rather than assumed. A feed
that fails to load contributes nothing **and** is named in `missing`, so a
partial total can never be mistaken for a complete one.

The Telegram report now prints the breakdown under the headline number, so the
figure is checkable rather than asserted. `dashboard/victoria_report.json` was
corrected in place ($41,578.25 → $36,578.25) so the dashboard stops showing the
wrong number before the next 08:00 ET run.

**Current real net worth: $36,578.25** — Robinhood $12,953.70, Kraken
$13,446.40, Truist MMA $9,500.00, Truist Checking $676.95, TrustWallet $1.20.

Note: TrustWallet's feed is **23 days stale** and now flags as such. Its
`sync_trustwallet.py` cron is `#HOLD`. At $1.20 it is immaterial to the total;
un-holding a cron is a scheduling change and was left for Jase.

## 3. Blade/Edge were NOT trading — and it was NOT "no setup" — FIXED

**Status before this session: zero real orders, ever.** 203 decisions logged
since the executor went live 2026-07-28, and the breakdown is damning:

| Outcome | Count | Share |
|---|---|---|
| `DAILY_DD_HALTED` | 169 | 83% |
| `ERROR` (OANDA 401) | 20 | 10% |
| `NO_SIGNAL` | 8 | 4% |
| `OUT_OF_KILLZONE` | 4 | 2% |
| `DRY_RUN_SIGNAL` | 2 | 1% |
| **`SIGNAL_FIRED`** | **0** | **0%** |

The strategy was only allowed to *evaluate* a setup 8 times in two days. This
was never a case of mean reversion not firing.

**Root cause: Blade and Edge shared one daily-drawdown circuit breaker across
two different accounts.** Both run the same executor on the same `*/15` cron
minute, against different OANDA practice books — `…-001` at $2,000 (Blade) and
`…-002` at $5,000 (Edge). The DD state file was keyed only by UTC date:
`/tmp/live_turtle_dd_<date>.json`. Whichever agent ticked first wrote **its own**
balance as `day_start_balance`; the other then measured its genuinely different
balance against that foreign anchor:

```
(2000 - 5000) / 5000 = -60%   ->  breaches the -4% rail  ->  halted
```

The halt is a day-scoped latch, so that one crossed wire stopped **both** agents
for the rest of every UTC day. `/tmp/live_turtle_dd_20260729.json` and
`…20260730.json` both show `halt_dd: -0.6`, latched ~10 seconds after the first
tick of the day. `dashboard/live_turtle_balance.json` was shared the same way.

**Fix.** Both files are now keyed on the **OANDA account id**, not the agent
name — `_book_key()`. That is the correct invariant: *one daily-drawdown rail
per book*. Two agents sharing one account **should** share a rail (it is the
same money); two agents on separate accounts must not. The rail can no longer be
anchored to a balance that isn't its own. Also added: a zero/negative anchor
re-anchors instead of dividing by itself.

**Verified.** Replaying the exact 07-29/07-30 sequence: each book now anchors to
its own balance, neither halts the other, and — importantly — **the rail still
bites**: Blade at -5% halts and stays latched, while Edge is unaffected.

Stale latched halt state for today was cleared so the next killzone tick runs
clean.

**First-fire alerts never triggered, and that was correct.** `live_turtle_first_fire.py`
only alerts on `SIGNAL_FIRED`, and no such record existed. The monitor itself is
healthy — heartbeating every 10th run, `waiting on: ['blade', 'edge']`, no
errors. It is armed and will fire on the first real order.
