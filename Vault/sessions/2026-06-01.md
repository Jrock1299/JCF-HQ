### Blade D3 redesign — the main work
1. Pulled the 287-trade backup from `/tmp/blade_reset_backup/agent_trades.json.bak`
2. Computed actual R:R math:
   - Avg ORB stop distance: ~11.4 pts (SPX500)
   - Old TPs (3/5/10pt) → R:R = 0.26 / 0.44 / 0.88 (sub-1R on TWO positions!)
   - Cluster-level PF on SPX500 alone: 0.34 — losing strategy
3. Found the sizing bug: code used `SL_BUFFER_POINTS` (3pt) as the
   divisor instead of real stop distance. Real risk was ~4× target.
4. Ran Monte Carlo on 4 candidate designs (100 sims × 250 clusters each):
   - CURRENT: PF 0.92, 25% DD
   - D1 (1R/2R/3R equal weight): PF 0.89 (worse)
   - D2 (0.75R/1.5R/3R equal weight): PF 0.88 (worse)
   - D3 (1R/2R/trail, 20/30/50 weights): PF 1.54, 25% DD, 0% ruin ← winner
5. Presented full proposal to user before implementing. Approved.
6. Implemented D3:
   - Real stop distance: `entry - orb_low - buffer` (long) / mirror (short)
   - Weighted sizing: 20/30/50 across pos1/2/3
   - TPs: 1R / 2R / null (trailing)
   - pos3 trail: activates on pos1 TP, distance = 1R below high-water
   - Compounding via `dashboard/blade_balance.json`
   - Daily DD circuit breaker at -4% (in `/tmp/blade_dd_<UTC-date>.json`)
   - `pos3_trail_r_achieved` logged as dedicated field for Norman validation
   - All knobs in `agent_strategies.json`; old keys kept as fallbacks
7. End-to-end test: simulated cluster lifecycle (TP1 → BE on pos2/3 →
   trail pos3 → trail-out on pullback). All R-multiples correct, balance
   compounds, DD state tracks.

### Blade `PIP_VALUE` accounting fix
- Closed the standing TODO at `blade_bot.py:154`. `PIP_VALUE` was conflating
  two unrelated quantities — price-increment-per-pip (used for stop
  placement and the sizing divisor) and dollar-per-pip (used for P&L).
  Identical for SPX500_USD, so that pair was correct; broken for DE30_EUR
  (EUR-denominated) and CHF_JPY (JPY-denominated).
- Added `QUOTE_CURRENCY`, `_fx_to_usd(ccy)` (live OANDA mid via existing
  `get_price()`, cached per-process), and `usd_per_pt_per_unit(instrument)`.
- Each position stamps `usd_per_pt` at entry time so the FX rate is locked
  in for the position's lifetime — attribution doesn't get smeared by
  intraday FX drift.
- Swapped `pip_value` → `usd_per_pt` in every P&L site: TP fills, SL fills,
  trail-out close, time-stop close, and the R-multiple denominator in
  `_record_learning` (so R-mult stays dimensionless on the non-USD pairs).
- **Sizing math unchanged** — `int(per_pos_risk_$ / (stop_pts × pip_value))`
  still uses the price-increment, per scope ("accounting only, do NOT
  change entry/exit/sizing").
